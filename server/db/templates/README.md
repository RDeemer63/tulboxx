# Data Migrations Guide  
_Tulboxx CRM – `server/db/templates`_

> **Why this folder exists**  
> Re-usable templates that make writing **data migrations** safe, consistent, and fast.

---

## 1  What belongs here?

* **Schema migrations** (create / alter / drop tables, columns, indexes)  
  – auto-generated by **Drizzle Kit** and live in the root `migrations/` folder.
* **Data migrations** (move, back-fill, transform, or clean data)  
  – hand-written using the TypeScript templates in **this directory**.

---

## 2  Schema vs. Data Migrations

| When the change is… | Migration type | Tool / location |
|---------------------|---------------|-----------------|
| Add / drop / rename tables, columns, indexes | **Schema** | `npx drizzle-kit generate` → `migrations/000X_*.sql` |
| Populate a new column from existing data | **Data** | Copy template → `server/db/data-migrations/` |
| Back-fill UUIDs, merge rows, parse JSON → columns | **Data** | Custom script |
| Change column type **and** convert existing values | Two-step: Schema then Data | 1. Drizzle migration, 2. data script |
| Pure cleanup of orphaned or duplicate rows | **Data** | Custom script |

Rule of thumb  
• DDL = **Schema** migration  • DML = **Data** migration

---

## 3  How to create & run a data migration

1. **Copy the template**

```bash
cp server/db/templates/data-migration-template.ts \
   server/db/data-migrations/20250616093000_my_migration.ts
```

2. **Edit constants** at the top  
   `MIGRATION_NAME` & `MIGRATION_DESCRIPTION`

3. **Implement** the `up(tx)` (and optional `down(tx)`) logic  
   Use the passed `tx` object for every query – this keeps the whole script transactional.

4. **Test locally**

```bash
npx tsx server/db/data-migrations/20250616093000_my_migration.ts up
```

5. **Run in production**

```bash
npx tsx server/db/data-migrations/20250616093000_my_migration.ts up \
  --confirm-production-data-migration
```

6. **Rollback** (only if `down()` is safe)

```bash
npx tsx path/to/script.ts down
```

## 4  Best practices

* **One concern per file** – small migrations are reviewable & reversible.
* **Idempotent** – `up()` should tolerate partial re-runs when possible.
* **Batch long jobs** – e.g. `LIMIT 500` with offset loop to avoid OOM.
* **Log progress** – `console.log` every batch so ops can see life-signs.
* **Wrap in one transaction** – template does this automatically.
* **Never edit an applied migration** – create a follow-up fix file.
* **Backup first in prod** – even with `down()`, restores are safer.
* **Code review checklist**
  1. Correct table/column names  
  2. Explains why, how, and rollback plan  
  3. Runtime tested on stage copy

---

## 5  How Drizzle Kit migrations & data migrations work together

1. Change your Drizzle **schema.ts**  
2. Run `npx drizzle-kit generate` – creates **schema** SQL in `migrations/`
3. Apply that SQL with `npm run db:migrate`
4. _If existing rows need adjusting_ → write a **data** migration in `server/db/data-migrations/`
5. Run the data migration manually (or via deploy script)

Keeping structure (DDL) and content (DML) in separate flows prevents accidental table locks, makes rollbacks clearer, and keeps Drizzle’s auto-generated SQL clean.

Happy (and safe) migrating 🛠️
